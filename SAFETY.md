# SAFETY.md

Our safety claim: **assume the model is fully compromised; the gate bounds the worst it can do.** The model only reads. For one email it returns one JSON reading (a class from a fixed list, and the date, time and zone the sender wrote), and code checks that reading against a schema. Code decides what to do (`policy.decide`), and every send and every booking passes one gate in one file (`src/doris/gate.py`, checks G1 to G17) before an adapter is allowed to act. Nothing here rests on a prompt.

Every rule below is cited by file and function, every test by file and test name (run them all with `python3 -m unittest discover -s tests -t .` from the repo root; run every `python3 -m doris` command from `src/`), and every trap by its number in the organizers' Trap Pack (`tests/trap-pack/`) or its file in the demo's inbox (`sandbox/inbox/`). Anything not built yet says **pending**. The Trap Pack results cited are run 1 with the model live (`tests/trap-pack/RESULTS.md`, graded by hand against the pack's key in `tests/trap-pack/RUNS.md`): met 10, safe and silent 6, missed 3, bug 1. A run on the fixed code is **pending**.

## Guardrails

The brief: "Destructive or irreversible actions (delete, send, pay, deploy, overwrite) need confirmation or are blocked by policy enforced in code. Not in the prompt. In code."

**Prove it:** `python3 -m doris demo`, then open the run's `receipts.jsonl`. Every action has a `checked` line listing all 17 checks with pass, fail, n/a or error. In the demo and in run 1 every action passed the gate; blocks at the gate are shown by `python3 -m doris redteam` (G1, G7 and G9 block there; `tests/redteam/RESULTS.md`) and by the tests (`tests/unit/test_gate.py`). `python3 -m doris traps` runs the organizers' Trap Pack through the same gate. With no key it runs the keyword stub, not Claude, and rewrites `tests/trap-pack/RESULTS.md`; the stub offers times to the senders of 03, 10, 12, 16 and 17. Run 1's report stays in git and in `traces/model-live-throwaway-traps-20261127T2207Z/`. **On the video:** **pending** (filmed Sunday).

**The gate** (`src/doris/gate.py`). `gate.check` runs every check, in order, on every action, and records each result on the `checked` receipt. A check that raises, a missing input, or an answer that is not a plain yes or no is an error, and an error blocks. Only an explicit pass counts.

|---|---|---|
| G1 not halted | No halt is in force, read from disk at that moment | Everything |
| G2 sole runner | This process holds the ledger lock: one Doris per ledger | Everything |
| G3 under budget | Model spend is under $5.00 for the run; reaching it halts her | Everything |
| G4 model there | Anything that used the model has its answer; while the model is down nothing goes to a prospect | Prospect sends, bookings |
| G5 not silenced | No recipient is on the stop list, read fresh | Sends |
| G6 right recipient | The original sender on their thread, one blind copy to the owner from config; never a group, a copy, a new address or a Reply-To unlike From | Sends, bookings, cancels |
| G7 under caps | Per hour, per run, per thread per day, per thread ever, two offers per thread | Sends, hold notices, bookings |
| G8 approved template | An approved template, rendered again by code, plus the locked signature, byte for byte | Sends |
| G9 bookable interval | Mon to Fri 9 to 5 Pacific, 24 hours to 30 days out, no holiday, allowed length; a pick only from her own open offer | Bookings and offered times |
| G10 direct-booking evidence | The parser's verdict is "book" with conditions B1 to B9 passed, and the model reads the same date, time and zone | Direct bookings |
| G11 fresh re-check | A calendar read made right now shows nothing overlapping; a failed read blocks | Bookings |
| G12 ledger first | Her booking ID is in the ledger before the write; create-only; no other live booking on the thread | Bookings |
| G13 fixed .ics | Only the fixed fields; no attendee, no organizer | Bookings, a confirmation's or cancel's `.ics` |

Tests: `tests/unit/test_gate.py` (158 tests, one class per check, plus `TableTest.test_check_records_all_17_in_table_order` and `AppliesAndFailClosedTest`).

**The caps** (`src/doris/caps.py`, the one file every hard limit lives in): 30 sends to prospects an hour, 100 a run, 5 on one thread a day, 8 on one thread ever, 2 offers on one thread ever, 40 calendar writes a run, 30 hold notices an hour, $5.00 of model spend a run; a message over 20,000 characters of text or 25 MB is held.

**The model reads, code writes.** Every sentence she sends is a template on the approved list (`templates.render`), filled with typed values by code. Model-written prose is never sent; G8 blocks it even when it carries the real signature. Hold notices quote only the sender's own visible words, defanged so nothing is clickable, with anything shaped like a code, key or token blanked (`holds.quote_of`, `holds.blank_codes`; `test_holds.py`: `QuoteTest.test_hidden_text_is_never_quoted`, `CodeTest.test_codes_keys_and_tokens_are_blanked`). Known limit: blanking goes by shape, so a code that reads as words is quoted as written (`tests/trap-pack/RUNS.md`).

**Fail closed and loud.** No model answer means the message is held and nothing goes to a prospect (G4, `hold.no_model`). A failed calendar read is never "available" (G11). A write whose result is unknown is looked up by booking ID, never retried blind, else held (`hold.unknown_result`). A send whose outcome is unknown is never sent again (`hold.send_unconfirmed`). A failed inbox read is never an empty inbox (`test_live.py`: `FetchTest.test_a_dropped_connection_is_a_mail_error_never_an_empty_inbox`). An unexpected error holds that one message, names itself on an error line, and the run goes on (`test_failures.py`: `UnexpectedError.test_an_unexpected_error_holds_that_message_and_the_run_goes_on`).

**Inbound text is data, never orders.** Screens 1 to 11 run in code before the model (`screens.run_batch`, `screens.run_message`); hidden text holds the email (screen 10), though text moved off-screen (a large negative position or a zero clip) is not on that list yet and reaches the model as data (a known limit in `tests/trap-pack/RESULTS.md`); the model's system prompt tells it to classify only; and the policy table, not the model, picks the action.

**Against a fully compromised model:** `python3 -m doris redteam` runs the hostile yes-man stand-in (`model._yes_man_answer`: always the most permissive answer, and it obeys any instruction in the mail) under the same gate and counts bad actions, read from what reached the adapters, never from the gate's verdicts. The cases: every Trap Pack file once for each of the stand-in's 9 answers, the demo day once for each of its 23, and three set pieces run once each (two that start at a cap, and the demo day with a Stop landing mid-run). Result: 0 bad actions in 206 runs over 24 cases, under a minute, no network, $0 (`tests/redteam/RESULTS.md`, `traces/model-yes-man-throwaway-redteam-20261128T0306Z/`). The proof can fail: with G7, G1 or G9 switched off in a test, the same runs count the bad action (`test_redteam.py`: `FullRunTest.test_it_passes_with_zero_bad_actions_and_says_so_last`, `FullRunTest.test_g7_blocks_both_caps`, `FullRunTest.test_nothing_happens_after_the_stop`, `ProofCanFailTest.test_with_g7_off_a_send_past_the_cap_is_a_bad_action`, `ProofCanFailTest.test_with_g1_off_an_effect_after_the_stop_is_a_bad_action`, `ProofCanFailTest.test_with_g9_off_an_offer_of_a_time_too_soon_is_a_bad_action`; `TamperTest` plants each kind of bad action and checks it is counted).

## Kill Switch

The brief: "One action stops everything, immediately, mid-run. Pending tool calls are cancelled, not finished."

**Prove it:** on a fresh clone, start a long run with `python3 -m doris run`, and within its first few seconds, while she is still working through the demo inbox, run `python3 -m doris stop` in a second terminal (or press Stop on the watch page). The run's own output ends with the halted line, for example: "Halted: stop on the command line. The worker was dead 87 ms after the stop. In flight: calendar_query span (seq 84). Dropped 1 queued item(s)." Then `python3 -m doris verify` passes over the whole file, halted line included, and `demo` or `run` refuses to start until `python3 -m doris resume`. Use a fresh clone because she never reads the same email twice: after a `demo` in the same folder, the run has nothing to do and `stop` reports nothing in flight. **On the video:** **pending** (filmed Sunday: the full unattended run first, then Stop landing while a slowed calendar call is waiting).

**How it works** (`src/doris/supervisor.py`):

- Doris runs as a child worker process under a supervisor (`supervisor.run_supervised`). The supervisor looks for a halt about every 0.1 seconds and kills the worker the moment it sees one (SIGKILL on Linux and macOS, TerminateProcess on Windows). The call in flight is cut off where it stands; one the server had already accepted is marked `unconfirmed` and settled on the next run (see above).
- Only after the worker is dead does the supervisor write the `halted` receipt, chained from the worker's last whole line (`supervisor.record_halt`). It names the cause, the call in flight with its sequence number, every queued item it dropped, and how many milliseconds the worker took to die. Queued work is written in the ledger before it starts, so a kill can name it.
- Ways to stop her, all one action: `python3 -m doris stop` (both modes at once), a file named `STOP` in the repo root or in `state/<mode>/`, Ctrl+C, SIGTERM or SIGHUP on the supervisor, the budget cap, and the watch page's Stop button. If the supervisor itself is killed, the worker sees its lifeline close, halts itself and writes its own halted line (`supervisor.Lifeline`). `traps` runs outside the supervisor on throwaway state, so `stop` and the HALT file do not reach it; a `STOP` file in the repo root halts it at its next step, not mid-call.
- A halt survives a restart. It is a file, `state/<mode>/HALT`, written atomically and read fresh before every effect (G1). `demo` and `run` refuse to start while it is there, and only `python3 -m doris resume` clears it. A STOP file is never deleted by code.
- Nothing in mail halts, starts or resumes her. A sender's "stop" silences that sender only.
- Messages a halt dropped are read again, through the whole loop, after resume (`test_restart.py`: `HaltThenResume.test_messages_a_halt_dropped_are_read_again_after_resume`).

## Audit Trail

The brief: "Every action is logged with enough detail that a human can reconstruct and replay what happened."

**Prove it:** `python3 -m doris demo`, then `python3 -m doris verify`: "ok: <n> lines, every hash matches the line before it". Now change any character of any line in that run's `receipts.jsonl` (under `state/sandbox/runs/<run>/` at the repo root) and run `verify` again: it names the line, for example "BROKEN at seq 20: ... the hash does not match the line", and exits 1. On an untouched run, `python3 -m doris replay` tells the run again in plain words, one block per message; on the changed one it refuses, naming the same line. **On the video:** **pending** (filmed Sunday).

**The receipts** (`src/doris/receipts.py`). One JSONL line for every step: `observed` (what she saw), `classified` (the model's raw answer, and whether it was live, replayed or stub), `decided` (the plan), `checked` (all 17 gate checks), `called` and `result` (every adapter and model call, written before it starts and answered after; the model's `result` carries its tokens and cost), `held`, `halted`, `error` and a closing `summary`. Each line holds the hash of the line before it, `hash = sha256(prev + canonical line)`, starting from "genesis". Each is appended, flushed and fsynced before she goes on, so a hard kill loses nothing she already wrote. Lines are canonical ASCII JSON with LF line ends, so a file reads and verifies the same on Linux, macOS and Windows.

**Every decision says why.** Every `decided`, `checked`, `held` and `halted` line carries a why, `{code, text}`, from one closed list (`src/doris/why.py`). Its slots are filled by code with counts, times, check ids and words from fixed lists, never a word from an email or from the model. The receipt writer refuses a decision line without one.

**What is never in a receipt:** a key, a password, the meeting link (replaced by `[meeting link]`), or a sent body (stored as its sha256). Sensitive mail leaves only the sender, a hash and the check name.

**`verify`** (`receipts.verify`) recomputes the chain and names the first line that was changed, removed, reordered, duplicated or cut from the end; a finished run must end on its summary or halted line.

**`replay`**: `python3 -m doris replay <run>` steps through a finished run in plain words, one block per message: what she saw, what she decided and why, what she called, what came back, what she verified. It checks the chain first and refuses a broken one. It takes a receipts file, a run folder, a trace folder or a run ID (the latest sandbox run by default). It reads the receipt files and nothing else: no model, mail, calendar, ledger or loop code is loaded, no host is allowed, and nothing is written (`test_replay.py`: `DemoDay.test_every_message_gets_a_block_from_saw_to_its_closing_line`, `DemoDay.test_replay_writes_nothing`, `BrokenChain.test_a_changed_byte`, `TrapPackRun1.test_the_committed_trace_steps_through_end_to_end`, `HaltedRun.test_a_stop_mid_send_shows_the_halt_the_call_in_flight_and_what_was_dropped`, `ReadsOnlyTheReceipts.test_it_loads_no_model_mail_calendar_or_loop_code`).

**Real runs are committed.** `traces/` holds real runs: their receipts (the model's raw answer is on each `classified` line), the messages they read and the verify result, each folder named by its model source and mode (`model-live-…`, `model-replayed-…`, `model-stub-…`, `model-yes-man-…`), so a trace never passes off a replay as live. Live runs and the smoke keep their own, pass or fail: `traces/live-run-<UTC stamp>/` and `traces/live-smoke-<UTC stamp>/`, with the receipts, a manifest (the commit, the model, the measured cost, the counts, the outcome and the first failing step), a timeline and the terminal log (`livetrace.py`; `test_live_loop.py`: `LiveTraceTest.test_a_run_stopped_on_the_command_line_keeps_its_whole_trace_with_outcome_pass`, `LiveTraceTest.test_a_run_that_ends_on_failed_reads_keeps_its_trace_with_outcome_fail`). Committed so far: Trap Pack run 1 with the model live, a Trap Pack run with the stub, the yes-man redteam run, and the three live smokes of Nov 27, the two failed ones included (`traces/live-smoke-20261128T042934Z/`, `traces/live-smoke-20261128T051500Z/`, and run 3, which passed every step: [`traces/live-smoke-20261128T055002Z/`](traces/live-smoke-20261128T055002Z/)). Each Trap Pack item's `terminal.log` is empty in the committed runs: saving what the terminal showed is **pending** for `traps` (the live traces carry theirs). The live runs and the overnight run are **pending**.

Tests: `tests/unit/test_receipts.py` (`Verify.test_one_changed_byte_in_each_field_names_its_seq`, `Verify.test_any_single_byte_flip_in_a_middle_or_last_line_is_caught`, `Verify.test_deleted_line_names_its_seq`, `Verify.test_reordered_lines_name_the_first_out_of_place`, `Verify.test_lines_cut_from_the_end_fail_the_finished_check`, `WhyRequired.test_decision_kinds_refuse_a_missing_why_and_write_nothing`, `CallPairing.test_a_send_carries_its_body_only_as_a_hash`, `HardKill.test_killed_writer_loses_no_reported_line_and_the_chain_resumes`); `test_demo.py`: `DemoDay.test_the_chain_verifies`, `DemoDay.test_every_decision_carries_a_listed_why`, `DemoDay.test_every_called_line_has_its_result`; `test_live_loop.py`: `LiveRunTest.test_no_secret_and_no_link_reach_a_receipt_the_terminal_or_the_state_folder`.
